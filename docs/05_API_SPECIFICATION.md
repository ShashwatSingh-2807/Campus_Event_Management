# CampusLoop — API Specification

**Document:** 05 — API Specification  
**Version:** 1.1  
**Status:** Draft baseline  
**API style:** REST over HTTPS, JSON  
**Base path:** `/api/v1`  
**Backend:** Python + FastAPI  
**Database:** PostgreSQL

---

## 1. Purpose and scope

This document defines the initial API contract between the CampusLoop web frontend and the FastAPI backend. It translates the PRD, TRD, Application Flow, and Database Design v1.1 into endpoint paths, request and response shapes, authorization rules, validation behavior, and error handling.

The API is designed for the single-college NIE Mysuru MVP. The backend remains the source of truth for identity verification, college affiliation, roles, event lifecycle, trusted publishing, registration eligibility, and capacity.

This is a proposed contract for implementation. It is not evidence that any endpoint has been built or tested. The OpenAPI document generated by FastAPI should be kept aligned with this specification as implementation proceeds.

### 1.1 In-scope capabilities

- Student registration, email verification, login, logout, refresh, and password reset.
- Current-user profile and registration history.
- Public event discovery and event detail.
- Organizer event creation and management.
- Trusted direct publishing and untrusted event approval.
- Material event revisions and administrator review.
- Individual registrations, cancellation, re-registration, and participant lists.
- Organizer dashboard and participant export.
- College-admin approval and organizer-trust management.

### 1.2 Out of scope for v1.0

- Team registrations and waitlists.
- Payments, refunds, and ticketing.
- QR attendance, check-in, and certificates.
- In-app chat and social features.
- Push notifications and a notification center.
- Native mobile-specific API behavior.
- Multi-college membership for one account.
- Full platform-admin management APIs beyond operational health and support needs.

## 2. Product and API rules

The API must preserve these confirmed product decisions:

1. **One college per account:** an account receives one college affiliation after successful verification of an approved institutional email. The client cannot choose or change its college.
2. **Verification is not organizer access:** verified students do not automatically become organizers.
3. **Organizer and trusted-publisher are separate:** organizer access is granted by a college administrator; trusted-publisher status is an additional attribute.
4. **Trusted initial publishing:** a trusted organizer can publish a valid new event directly. An untrusted organizer submits a new event for college-admin approval.
5. **Approved-event edits require review:** material edits to an already-approved event are stored as a separate revision. The last approved event remains public until a college administrator approves the revision. Trusted status does not bypass this rule.
6. **Individual registrations only:** one student can have one registration row per event.
7. **Re-registration is allowed:** after cancelling, a student can reactivate the same registration while registration is open and capacity remains.
8. **Capacity is authoritative on the backend:** client-side seat counts are informational only. The registration transaction must enforce capacity under concurrency.
9. **College isolation:** college administrators and organizers can access only resources within their authorized college and club scope.

## 3. Base URL and conventions

### 3.1 Base URL

Local development example:

`http://localhost:8000/api/v1`

Deployed environments must use HTTPS. The production hostname is environment-specific and is not fixed in this document.

### 3.2 Request and response format

- JSON request bodies use `Content-Type: application/json`.
- JSON responses use `Content-Type: application/json`, except CSV exports and empty responses.
- Property names use `snake_case`.
- Resource identifiers are UUID strings.
- Timestamps use ISO 8601 / RFC 3339 with an explicit timezone offset. Responses should be normalized to UTC using a `Z` suffix.
- Unknown request properties should be rejected for write operations rather than silently persisted.
- Database models must not be serialized directly. Use dedicated Pydantic request and response schemas.

### 3.3 HTTP methods

| Method | Intended use |
|---|---|
| GET | Read a resource or collection; must not mutate data |
| POST | Create a resource or execute a domain action |
| PATCH | Partially update permitted fields |
| DELETE | Not used for normal MVP business workflows; preserve history through status changes |

### 3.4 Pagination

Collection endpoints use page-based pagination.

Query parameters:
- `page`: 1-based page number; default 1.
- `page_size`: number of records; default 20; minimum 1; maximum 100.

Standard collection response:

~~~json
{
  "items": [],
  "pagination": {
    "page": 1,
    "page_size": 20,
    "total_items": 0,
    "total_pages": 0
  }
}
~~~

Sort order must be deterministic. When sorting by a date, add the resource ID as a tie-breaker.

### 3.5 Filtering and sorting

- Unsupported filter names or sort values return `400 INVALID_QUERY_PARAMETER`.
- Public event search returns only public event states; clients cannot request drafts, pending approvals, rejected events, or private organizer data.
- All organizer and administrator collection queries are automatically scoped by the authenticated user's permissions. A client-supplied college ID must never widen access.

### 3.6 Authentication header

Protected requests use:

~~~http
Authorization: Bearer <short_lived_access_token>
~~~

The access token is short-lived. The web client should keep it in memory rather than browser local storage.

### 3.7 Refresh-token cookie

The refresh endpoint uses a server-managed refresh-session cookie:

- Cookie name: `campusloop_refresh` (implementation default; configurable).
- Flags: `HttpOnly`, `Secure` in deployed environments, and `SameSite=Lax` or stricter according to deployment topology.
- Cookie path should be restricted to the authentication routes where practical.
- The raw refresh token is never returned in JSON and is never stored in local storage.
- The backend stores only a hash of the refresh token and rotates it on use.
- Refresh and logout requests must enforce the configured allowed Origin / Fetch Metadata policy and same-site protections.
- Logout clears the cookie and revokes the server-side refresh session.

Cookie domain, lifetime, access-token lifetime, and cross-origin settings are deployment configuration, not hard-coded API behavior.

## 4. Authentication and authorization

### 4.1 Roles and attributes

| Role / attribute | Meaning |
|---|---|
| `STUDENT` | Verified user assigned to one college |
| `ORGANIZER` | User explicitly granted organizer access |
| `COLLEGE_ADMIN` | Administrator for one college |
| `PLATFORM_ADMIN` | Platform-wide operator |
| `is_trusted_publisher` | Separate organizer attribute; not a role |

A user may hold more than one applicable role within the same college. The backend must evaluate the combination of role, college scope, club membership, resource ownership, and event state.

### 4.2 Authorization matrix

| Operation | Visitor | Verified student | Assigned organizer | College admin |
|---|---:|---:|---:|---:|
| Browse public events | Yes | Yes | Yes | Yes |
| View public event details | Yes | Yes | Yes | Yes |
| Register / cancel own registration | No | Yes, when eligible | Only if separately eligible as student | Only if separately eligible as student |
| View own profile and registrations | No | Yes | Yes | Yes |
| Create/manage assigned club events | No | No | Yes | Only if separately authorized |
| View participants for assigned events | No | No | Yes | Yes, within college |
| Publish a new event directly | No | No | Trusted publishers only | According to explicit admin policy |
| Submit a new event for approval | No | No | Yes | According to explicit admin policy |
| Approve/reject initial submissions | No | No | No | Yes, within college |
| Submit a material event revision | No | No | Yes, for assigned event | According to explicit admin policy |
| Approve/reject a material revision | No | No | No | Yes, within college |
| Grant/revoke organizer trust | No | No | No | Yes, within college |

The API does not infer permissions from frontend routes or navigation. Every protected endpoint independently enforces authorization.

### 4.3 College scoping

- The active college is derived from the authenticated user and stored server-side.
- A verified account has one college affiliation in the MVP.
- Organizer profiles, clubs, events, registrations, and administrative queues must be checked against that college.
- Resource lookups must avoid leaking whether a resource exists in another college. Return `404 RESOURCE_NOT_FOUND` when the caller is outside the resource's allowed scope, unless a generic `403` is more appropriate for a known action-level denial.
- Never trust `college_id`, `role`, `is_trusted_publisher`, `created_by_user_id`, or `student_user_id` supplied by the client as proof of authority.

The following schemas describe public API shapes, not SQLAlchemy model definitions. Fields marked optional may be omitted or null as indicated.

~~~json
{
  "id": "uuid",
  "email": "student@college.example",
  "full_name": "Aarav Kumar",
  "email_verified": true,
  "college": {
    "id": "uuid",
    "name": "NIE Mysuru",
    "slug": "nie-mysuru"
  },
  "roles": ["STUDENT"],
  "created_at": "2026-11-03T10:00:00Z"
}
~~~

Do not expose password hashes, verification-token hashes, refresh-token hashes, internal audit metadata, or session secrets.

### 5.2 Event summary

~~~json
{
  "id": "uuid",
  "title": "Campus Hackathon",
  "summary": "A 24-hour student hackathon.",
  "category": {
    "id": "uuid",
    "name": "Technical",
    "slug": "technical"
  },
  "club": {
    "id": "uuid",
    "name": "Coding Club"
  },
  "starts_at": "2026-12-12T04:00:00Z",
  "ends_at": "2026-12-13T04:00:00Z",
  "timezone": "Asia/Kolkata",
  "venue": "Main Auditorium",
  "is_online": false,
  "capacity": 200,
  "eligibility_notes": "Open to all verified undergraduate students.",

  "registration_opens_at": "2026-11-15T04:30:00Z",

~~~

Public event responses must not include participant lists, organizer trust notes, approval comments, private meeting credentials, or internal audit fields.

### 5.3 Event detail

In addition to the summary fields, event detail can include:
- `description`
- `eligibility_notes` (optional)
- `contact_email` (optional)
- `meeting_url` only when disclosure is permitted by event policy
- `capacity_remaining` when capacity is limited
- `registration_open`
- `content_version`
- `published_at`

The response must clearly communicate whether an event is cancelled or registration is closed. Draft, pending, and rejected events are not returned through public event-detail endpoints.

### 5.4 Registration

~~~json
{
  "id": "uuid",
  "event_id": "uuid",
  "status": "REGISTERED",
  "registered_at": "2026-11-03T11:15:00Z",
  "cancelled_at": null
}
~~~

A student's registration response must not expose another student's information.

### 5.5 Organizer participant item

~~~json
{
  "registration_id": "uuid",
  "student": {
    "id": "uuid",
    "full_name": "Aarav Kumar",
    "email": "student@college.example"
  },
  "status": "REGISTERED",
  "registered_at": "2026-11-03T11:15:00Z"
}
~~~

Participant email is exposed only to an organizer or administrator authorized for that event. Do not expose password, token, session, or unrelated profile data.

## 7. Authentication endpoint contracts

### 7.1 POST /auth/register

Creates an account in an unverified state and sends a one-time verification link or code.

Request:

~~~json
{
  "full_name": "Aarav Kumar",
  "email": "student@college.example",
  "password": "A-long-user-chosen-password"
}
~~~

Rules:
- Normalize email to lowercase and trim surrounding whitespace.
- Validate the email domain against active configured college domains.
- The client must not send `college_id` or roles.
- Store only an Argon2id password hash.
- Assign no student role and no college affiliation until verification succeeds.
- Rate-limit by IP and normalized email.
- Never return the verification token in the API response.

Success: `202 Accepted`

~~~json
{
  "message": "If the address is eligible, verification instructions will be sent."
}
~~~

Potential errors: `422 VALIDATION_ERROR`, `422 INSTITUTIONAL_EMAIL_NOT_SUPPORTED`, `429 RATE_LIMITED`. Avoid account-enumeration details in responses where possible.

### 7.2 POST /auth/verify-email

Verifies ownership of the institutional email. On success, consumes the token, assigns the college inferred from its configured domain, marks email as verified, and grants the STUDENT role.

Request:

~~~json
{
  "token": "one-time-verification-token"
}
~~~

Success: `200 OK`

~~~json
{
  "message": "Email verified successfully.",
  "user": {
    "id": "uuid",
    "email": "student@college.example",
    "email_verified": true,
    "college": {
      "id": "uuid",
      "name": "NIE Mysuru",
      "slug": "nie-mysuru"
    },
    "roles": ["STUDENT"]
  }
}
~~~

Errors: `400 INVALID_OR_EXPIRED_TOKEN`, `409 EMAIL_ALREADY_VERIFIED`, `429 RATE_LIMITED`.

The token must be single-use and expire. Verification and college assignment must occur in one database transaction.

### 7.3 POST /auth/resend-verification

Requests a replacement verification message for an account that has not yet completed email verification.

Request:

~~~json
{
  "email": "student@college.example"
}
~~~

Success: `202 Accepted`

~~~json
{
  "message": "If an eligible unverified account exists, verification instructions will be sent."
}
~~~

Security and behavior:
- Return the same generic response whether the account exists, is already verified, is unsupported, or is not eligible. Do not expose account existence.
- If an eligible unverified account exists, create a new single-use token and send the verification message.
- Invalidate or consume prior unexpired verification tokens for that user so only the newest message remains usable.
- Apply rate limits per IP and normalized email address. The exact cooldown and daily limit are deployment configuration.
- Never return the raw token or place it in application logs.
- Expired or consumed tokens remain unusable.

No content is returned about the account state. Errors are limited to malformed input (`422 VALIDATION_ERROR`) or throttling (`429 RATE_LIMITED`).

### 7.4 POST /auth/login

Request:

~~~json
{
  "email": "student@college.example",
  "password": "A-long-user-chosen-password"
}
~~~

Success: `200 OK`. Return a short-lived access token and set the HttpOnly refresh cookie.

~~~json
{
  "access_token": "short-lived-access-token",
  "token_type": "Bearer",
  "expires_in": 900,
  "user": {
    "id": "uuid",
    "email": "student@college.example",
    "full_name": "Aarav Kumar",
    "email_verified": true,
    "roles": ["STUDENT"]
  }
}
~~~

Errors:
- `401 INVALID_CREDENTIALS` for invalid email/password combinations.
- `403 EMAIL_VERIFICATION_REQUIRED` for an account that has not been verified.
- `403 ACCOUNT_SUSPENDED` for a suspended account.
- `429 RATE_LIMITED` when throttled.

Do not reveal whether an email address exists in the system. Apply login rate limits and safe password verification behavior.

### 7.5 POST /auth/refresh

Reads the refresh cookie, validates the session, rotates the refresh token, revokes/replaces the old session token, sets the new cookie, and returns a new access token.

Request body: none.

Success: `200 OK`

~~~json
{
  "access_token": "new-short-lived-access-token",
  "token_type": "Bearer",
  "expires_in": 900
}
~~~

Errors: `401 REFRESH_SESSION_INVALID`, `401 REFRESH_SESSION_EXPIRED`, `401 REFRESH_TOKEN_REUSE_DETECTED`, `429 RATE_LIMITED`.

Refresh-token reuse detection should revoke the affected session family and write a security audit event. The raw refresh token must never be returned in JSON.

### 7.6 POST /auth/logout

Revokes the current refresh session, clears the refresh cookie, and invalidates the current authenticated session according to the token strategy.

Request body: none.

Success: `204 No Content`.

Logout should be safe to retry. The endpoint must enforce allowed Origin / same-site protections for cookie-authenticated requests.

### 7.7 POST /auth/forgot-password

Request:

~~~json
{
  "email": "student@college.example"
}
~~~

Success: `202 Accepted`

~~~json
{
  "message": "If an eligible account exists, password reset instructions will be sent."
}
~~~

Always use a generic response so callers cannot discover registered email addresses. Store only a hash of the one-time reset token. Apply rate limits.

### 7.8 POST /auth/reset-password

Request:

~~~json
{
  "token": "one-time-password-reset-token",
  "new_password": "A-new-long-password"
}
~~~

Success: `204 No Content`.

The token must be unexpired and single-use. Revoke existing refresh sessions after a successful password reset. Errors: `400 INVALID_OR_EXPIRED_TOKEN`, `422 VALIDATION_ERROR`, `429 RATE_LIMITED`.

## 8. Current-user endpoint contracts

### 8.1 GET /users/me

Returns the authenticated user's profile, college, and current permissions.

Success: `200 OK` with the Authenticated User schema.

### 8.2 PATCH /users/me

Request:

~~~json
{
  "full_name": "Aarav K."
}
~~~

Only explicitly permitted profile fields may be changed. In v1.0, `full_name` is editable. Email, college affiliation, verification state, account status, roles, and trust attributes are not client-editable.

Success: `200 OK` with the updated user representation.

Errors: `401 UNAUTHENTICATED`, `422 VALIDATION_ERROR`.

- `page`, `page_size`.

Success: `200 OK` with a paginated list of registration records plus their public event summary. The user ID is taken from the access token; no user ID query parameter is accepted.

## 9. Public discovery endpoint contracts

### 9.1 GET /event-categories

Returns active event categories for discovery filters and organizer event forms.

Success: `200 OK`

~~~json
{
  "items": [
    {
      "id": "uuid",
      "name": "Technical",
      "slug": "technical"
    }
  ]
}
~~~

### 9.2 GET /events

Returns only public event records. Draft, pending-approval, and rejected events must never appear.

Query parameters:
- `q`: optional search across title and summary.
- `category_id`: optional UUID.
- `starts_after`: optional timestamp.
- `starts_before`: optional timestamp.
- `is_online`: optional boolean.
- `registration_open`: optional boolean filter.
- `sort`: `starts_at_asc` (default) or `starts_at_desc`.
- `page`, `page_size`.

Success: `200 OK` with a paginated list of Event Summary items.

The API must not trust a client-supplied college filter to widen access. For the initial single-college pilot, the public catalogue is scoped to the active pilot institution. Any later multi-college discovery behavior requires a separate product and authorization decision.

### 9.3 GET /events/{event_id}

Returns a public event detail. Publicly visible states are `PUBLISHED`, `REGISTRATION_CLOSED`, `ONGOING`, and `COMPLETED`. A previously published cancelled event may be returned by direct link with a clear cancellation status; it must not appear as an available event in normal discovery results.

Draft, pending-approval, rejected, unknown, or out-of-scope event IDs return `404 RESOURCE_NOT_FOUND` to public callers.

Success: `200 OK` with Event Detail.

The public response must not expose internal approval history, private organizer notes, or participant information.

## 10. Event creation and management contracts

### 10.1 Event write schema

Create and update requests use the following editable fields:

~~~json
{
  "club_id": "uuid",
  "category_id": "uuid",
  "title": "Campus Hackathon",
  "summary": "A 24-hour student hackathon.",
  "description": "Full event description.",
  "venue": "Main Auditorium",
  "is_online": false,
  "meeting_url": null,
  "starts_at": "2026-12-12T09:30:00+05:30",
  "ends_at": "2026-12-13T09:30:00+05:30",
  "registration_opens_at": "2026-11-15T10:00:00+05:30",
  "registration_closes_at": "2026-12-11T00:00:00+05:30",
  "timezone": "Asia/Kolkata",
  "capacity": 200,
  "eligibility_notes": "Open to all verified undergraduate students.",
  "contact_email": "codingclub@college.example"
}
~~~

The authenticated organizer identity and college are derived from the access token and database relationships. The client cannot set `created_by_user_id`, `college_id`, event status, approval fields, or publication timestamp.

Validation:
- Title is required and limited to 180 characters.
- Summary is required and limited to 300 characters.
- Description is required and must satisfy configured length limits.
- Category and club must exist, be active, and belong to the organizer's college.
- Organizer must have an active OWNER or EDITOR membership in the selected club.
- End time must be after start time.
- Registration opening must be before registration closing.
- Registration closing must not be after the event start time.
- Capacity must be null (unlimited) or a positive integer.
- `eligibility_notes` is optional plain text with a documented maximum length (recommended 2,000 characters).
- `contact_email` is optional; when supplied, validate and normalize it as an email address.
- For an in-person event, venue is required and meeting URL should be null.
- For an online event, meeting URL must be a valid permitted URL; venue may contain an optional display label.
- All timestamp values must include a timezone offset.

### 10.2 POST /events

Creates an event in `DRAFT` state.

Request: Event write schema.

Success: `201 Created` with the created event representation and a Location header pointing to `/api/v1/events/{event_id}`.

Errors: `401 UNAUTHENTICATED`, `403 ORGANIZER_ACCESS_REQUIRED`, `404 CLUB_NOT_FOUND`, `422 VALIDATION_ERROR`.

### 10.3 PATCH /events/{event_id}

Edits an event while it is in `DRAFT` or `REJECTED`. A rejected event can be corrected and submitted again.

Request: partial Event write schema. Immutable fields and status fields are rejected.

Success: `200 OK` with updated event representation.

Errors: `404 RESOURCE_NOT_FOUND`, `403 EVENT_MANAGEMENT_FORBIDDEN`, `409 EVENT_STATE_CONFLICT`, `422 VALIDATION_ERROR`.

Once an event has been approved/published, material changes must use the revision workflow in Section 11. Direct PATCH of approved event content is rejected.

### 10.4 POST /events/{event_id}/submit

Submits a valid draft or corrected rejected event for college-admin review. Intended for organizers who do not currently have trusted-publisher status.

Request:

~~~json
{
  "comment": "Please review this event."
}
~~~

The comment is optional.

Success: `202 Accepted` with the event in `PENDING_APPROVAL` state.

Errors: `403 TRUSTED_PUBLISHER_DIRECT_PUBLISH` when a trusted organizer attempts to use the approval path contrary to the configured flow, `404 RESOURCE_NOT_FOUND`, `409 EVENT_STATE_CONFLICT`, `422 VALIDATION_ERROR`.

### 10.5 POST /events/{event_id}/publish

Publishes a valid new event directly when the organizer is trusted.

Request body: none.

Success: `200 OK` with event status `PUBLISHED` and `published_at`.

Errors: `403 TRUSTED_PUBLISHER_REQUIRED`, `404 RESOURCE_NOT_FOUND`, `409 EVENT_STATE_CONFLICT`, `422 VALIDATION_ERROR`.

This endpoint is for initial publication only. It cannot be used to bypass review of material edits to an already-published event.

### 10.6 POST /events/{event_id}/cancel

Cancels an event managed by the caller, or by a college administrator within their college.

Request:

~~~json
{
  "reason": "Venue became unavailable."
}
~~~

A cancellation reason is required. Success: `200 OK` with status `CANCELLED`, cancellation reason, and updated timestamp.

The operation must be transactional and audited. Existing registration rows are retained; they are not deleted. Cancellation does not automatically send notifications in v1.0 because notification delivery is outside the current scope.

Errors: `403 EVENT_MANAGEMENT_FORBIDDEN`, `404 RESOURCE_NOT_FOUND`, `409 EVENT_STATE_CONFLICT`, `422 VALIDATION_ERROR`.

## 11. Material event revision contracts

### 11.1 POST /events/{event_id}/revisions

Submits proposed changes to an already-approved event without changing the public approved event.

Request:

~~~json
{
  "base_content_version": 3,
  "proposed_data": {
    "category_id": "uuid",
    "title": "Campus Hackathon — Updated",
    "summary": "A 24-hour student hackathon.",
    "description": "Updated event details.",
    "venue": "Seminar Hall",
    "is_online": false,
    "meeting_url": null,
    "starts_at": "2026-12-12T09:30:00+05:30",
    "ends_at": "2026-12-13T09:30:00+05:30",
    "registration_opens_at": "2026-11-15T10:00:00+05:30",
    "registration_closes_at": "2026-12-11T00:00:00+05:30",
    "timezone": "Asia/Kolkata",
    "capacity": 200
  }
}
~~~

Rules:
- The caller must be an active OWNER or EDITOR for the event's club.
- Proposed data is a complete snapshot of supported editable fields, including `eligibility_notes` and `contact_email`, not an arbitrary patch document.
- Validate all proposed data using the same event validation rules as initial event creation.
- `base_content_version` must match the current event `content_version`.
- Only one pending revision may exist per event.
- Once submitted, the proposal is immutable.
- A trusted publisher must also submit material changes for review.

Success: `202 Accepted` with a revision object in `PENDING_APPROVAL` state.

Errors: `404 RESOURCE_NOT_FOUND`, `403 EVENT_MANAGEMENT_FORBIDDEN`, `409 REVISION_ALREADY_PENDING`, `409 STALE_CONTENT_VERSION`, `422 VALIDATION_ERROR`.

### 11.2 GET /organizer/events/{event_id}/revisions

Returns revisions for an event that the caller is authorized to manage. Includes revision ID, version, base content version, status, created timestamp, and review timestamp. Do not return private reviewer information unless the caller is authorized to view it.

Success: `200 OK` with a paginated collection.

### 11.3 GET /admin/event-revisions/pending

Lists pending revisions within the college administrator's college scope.

Query parameters: `page`, `page_size`, optional `club_id`.

Success: `200 OK` with revision summary and current approved event summary. The query must never return revisions from another college.

### 11.4 POST /admin/event-revisions/{revision_id}/approve

Approves a pending material revision.

Request:

~~~json
{
  "comment": "Venue and schedule update reviewed."
}
~~~

On approval, the backend must, in one transaction:
1. Lock the event and revision rows.
2. Verify the revision is still pending.
3. Verify `base_content_version` still matches the event's `content_version`.
4. Revalidate the proposed event data and check that a capacity reduction does not go below current active registrations.
5. Apply the proposed fields to the event.
6. Increment `content_version`.
7. Mark the revision approved and insert an approval-history row.
8. Write an audit log entry.

Success: `200 OK` with the updated event and approved revision status.

Errors: `404 RESOURCE_NOT_FOUND`, `403 COLLEGE_ADMIN_REQUIRED`, `409 REVISION_NOT_PENDING`, `409 STALE_CONTENT_VERSION`, `409 CAPACITY_BELOW_REGISTERED_COUNT`, `422 VALIDATION_ERROR`.

### 11.5 POST /admin/event-revisions/{revision_id}/reject

Rejects a pending revision.

Request:

~~~json
{
  "reason": "The proposed venue is not approved for this event."
}
~~~

A rejection reason is required. The event's currently approved public fields remain unchanged.

Success: `200 OK` with revision status `REJECTED`.

Errors: `404 RESOURCE_NOT_FOUND`, `403 COLLEGE_ADMIN_REQUIRED`, `409 REVISION_NOT_PENDING`.

## 13. Registration and participant contracts

### 13.1 POST /events/{event_id}/registrations

Registers the authenticated student for the event, or reactivates their existing cancelled registration.

Request body: none. The student identity is taken only from the access token.

Business checks:
- Caller is authenticated, active, email-verified, and affiliated with the same college as the event.
- Event is published and the registration window is open.
- Event is not cancelled.
- Caller is not already actively registered.
- If a cancelled registration exists, registration can be reactivated only if capacity is available.
- The event row is locked (or an equivalent tested atomic strategy is used) while checking capacity and writing the registration.
- A registration status-history row is created in the same transaction.

First registration success: `201 Created`.

Re-registration success: `200 OK`.

~~~json
{
  "registration": {
    "id": "uuid",
    "event_id": "uuid",
    "status": "REGISTERED",
    "registered_at": "2026-11-03T11:15:00Z",
    "cancelled_at": null
  },
  "outcome": "CREATED"
}
~~~

For re-registration, `outcome` is `REACTIVATED`.

Errors:
- `401 UNAUTHENTICATED`
- `403 EMAIL_VERIFICATION_REQUIRED`
- `403 COLLEGE_MISMATCH`
- `404 RESOURCE_NOT_FOUND`
- `409 ALREADY_REGISTERED`
- `409 REGISTRATION_NOT_OPEN`
- `409 REGISTRATION_CLOSED`
- `409 EVENT_CANCELLED`
- `409 EVENT_CAPACITY_REACHED`
- `429 RATE_LIMITED`

The capacity check and insert/reactivation must be in one transaction. A frontend availability display is not a guarantee that a seat will still be available when the request reaches the server.

### 13.2 GET /events/{event_id}/registrations

Lists active and/or cancelled participants for an event when the caller is an authorized organizer for that event or a college administrator in the same college.

Query parameters:
- `status`: optional `REGISTERED` or `CANCELLED`; default `REGISTERED`.
- `q`: optional participant name or institutional email search.
- `page`, `page_size`.

Success: `200 OK` with paginated Organizer Participant items.

Unauthorized users must not be able to use this endpoint to discover whether a student is registered. Return `404 RESOURCE_NOT_FOUND` for out-of-scope events.

### 13.3 POST /registrations/{registration_id}/cancel

Cancels the authenticated user's own active registration.

Request:

~~~json
{
  "reason": "Unable to attend."
}
~~~

The reason is optional. The backend verifies ownership and cancellation eligibility, sets status to `CANCELLED`, sets `cancelled_at`, and appends a registration-status-history record in one transaction.

Success: `200 OK` with the updated registration.

Errors: `404 RESOURCE_NOT_FOUND`, `409 REGISTRATION_ALREADY_CANCELLED`, `409 CANCELLATION_NOT_ALLOWED`.

**Confirmed MVP cancellation cutoff:** A student may cancel their active registration at any time strictly before the event's `starts_at` timestamp. At or after the event start time, self-cancellation is not allowed. The check uses server time and the event timestamp normalized to UTC; the browser clock is not authoritative. This is a fixed MVP rule, not a per-event organizer setting. The API returns `409 CANCELLATION_NOT_ALLOWED` once the cutoff has passed.

### 13.4 Re-registration behavior

Re-registration does not create a second registration row. If the current row is `CANCELLED`, the API reactivates that row, updates its latest `registered_at`, clears `cancelled_at`, and appends a `CANCELLED → REGISTERED` history entry. The same registration endpoint is used; no separate re-register endpoint is required.

~~~json

  "user_id": "uuid",
  "club_id": "uuid",
  "membership_role": "EDITOR"
}
~~~

- Confirm the target user is verified and belongs to the administrator's college.
- Confirm the club belongs to the administrator's college.

## 16. Standard error format

All API errors use a consistent envelope.

~~~json
{
  "error": {
    "code": "REGISTRATION_CLOSED",
    "message": "Registration for this event is closed.",
    "details": [],
    "request_id": "req_01J..."
  }
}
~~~

For field validation errors:

~~~json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "One or more fields are invalid.",
    "details": [
      {
        "field": "ends_at",
        "issue": "must be later than starts_at"
      }
    ],
    "request_id": "req_01J..."
  }
}
~~~

- `details` is an array and may be empty.
- `request_id` is a correlation identifier for logs and support.
- Error messages must be safe for end users.
- Never return stack traces, SQL statements, database hostnames, secrets, token values, or internal exception details.
- FastAPI's default validation output should be adapted to this common envelope.

### 16.1 HTTP status-code guide

| Status | Use |
|---|---|
| 200 OK | Successful read or update/action with a response body |
| 201 Created | New resource created |
| 202 Accepted | Verification, password reset, or review submission accepted for processing |
| 204 No Content | Successful action with no response body, such as logout/reset completion |
| 400 Bad Request | Malformed request or invalid action syntax |
| 401 Unauthorized | Missing, invalid, or expired access credentials |
| 403 Forbidden | Authenticated caller lacks the required role or permission |
| 404 Not Found | Resource absent or deliberately hidden due to scope |
| 409 Conflict | Business-state conflict, duplicate active registration, or capacity conflict |
| 422 Unprocessable Entity | Request schema or field validation failure |
| 429 Too Many Requests | Rate limit exceeded |
| 500 Internal Server Error | Unexpected server failure; return only a safe generic message |
| 503 Service Unavailable | Required dependency unavailable or service not ready |

Do not use `200 OK` for failed business operations. Use stable machine-readable error codes so the frontend can display the correct state.

### 16.2 Initial error-code catalogue

| Code | Meaning |
|---|---|
| `UNAUTHENTICATED` | Access token missing, invalid, or expired |
| `INVALID_CREDENTIALS` | Login failed |
| `EMAIL_VERIFICATION_REQUIRED` | Account email is not verified |
| `INSTITUTIONAL_EMAIL_NOT_SUPPORTED` | Email domain is not configured for the pilot |
| `ACCOUNT_SUSPENDED` | Account cannot authenticate or use protected features |

## 17. Security and privacy requirements

1. Use HTTPS for all deployed API traffic.
2. Hash passwords using Argon2id and one-time tokens using a cryptographic hash.
3. Return short-lived access tokens and rotate refresh tokens with server-side session tracking.
4. Keep refresh tokens in secure HttpOnly cookies; do not store authentication secrets in local storage.
5. Enforce CORS with an explicit allowlist of web origins.
6. Apply rate limiting to registration, login, verification, password reset, and other abuse-prone endpoints.
7. Normalize and validate email addresses, URLs, timestamps, and all user-controlled data.
8. Use parameterized ORM queries.
9. Enforce college and club scope on every protected query.
10. Return minimum necessary participant information and restrict CSV exports.
11. Protect cookie-authenticated requests using same-site and Origin / Fetch Metadata validation.
12. Never log passwords, raw tokens, or complete refresh-cookie values.
13. Record security-sensitive actions such as trust changes, role grants, approvals, rejections, cancellations, revision approvals, and participant exports.
14. Apply a retention policy to session metadata and audit information before production use.

## 18. Transaction and consistency requirements

### 18.1 Registration

Registration and reactivation must use one transaction:
1. Lock the event row (or use an equivalent proven atomic capacity strategy).
2. Validate college, verification, event state, and registration window.
3. Read the existing student/event registration.
4. Reject if already active.
5. Count active registrations and verify capacity.
6. Insert a new registration or reactivate the cancelled row.
7. Append registration-status history.
8. Commit.

The unique constraint on `(event_id, student_user_id)` is the final duplicate defense.

### 18.2 Initial event approval

Approval/rejection, event state change, approval-history creation, and audit logging should occur in one transaction.

### 18.3 Event revision approval

Lock the event and revision. Verify the revision is pending and the base content version still matches. Apply approved data, increment content version, update revision status, add approval history, and add audit log in one transaction.

### 18.4 Organizer trust changes

Update the organizer profile and append an audit log in one transaction.

### 18.5 Retry behavior

The frontend should avoid accidental duplicate submissions by disabling actions while requests are in flight. Backend unique constraints and state checks remain mandatory. Do not assume that a client retry means the first request failed; the client should refresh resource state after an ambiguous network failure.

## 19. Testing requirements

### Authentication tests
- A supported institutional domain can register.
- An unsupported domain cannot create an eligible student account.
- Verification tokens expire and can only be used once.
- Resend verification uses a generic response, invalidates prior active tokens, and is rate-limited.
- College affiliation is assigned by the backend after verification.
- Login rejects invalid credentials and unverified accounts.
- Refresh rotates tokens and detects reuse.
- Password reset revokes existing refresh sessions.

### Authorization tests
- A student cannot access organizer endpoints without explicit organizer access.
- An organizer cannot manage a club they are not assigned to.
- A college administrator cannot review another college's events.
- A client cannot assign itself a role, college, or trusted status.
- Out-of-scope resources do not leak through list or detail endpoints.

### Event tests
- A new untrusted organizer event enters pending approval.
- A trusted organizer can publish a valid new event directly.
- An event cannot be published with invalid dates or capacity.
- A draft can be edited; an approved event cannot be directly patched.
- Pending revision data does not replace public approved event data.
- Only a college admin can approve/reject a pending revision.
- A stale revision cannot overwrite newer event content.
- A capacity reduction below active registrations is rejected.
- Cancellation retains existing registration records.

### Registration tests
- Only verified students of the event's college can register.
- Duplicate active registrations are rejected.
- Cancellation changes status and records history.
- Re-registration reactivates the same row.
- Re-registration fails when the registration window is closed or capacity is full.
- Concurrent attempts for the final seat never exceed capacity.
- A student cannot cancel another student's registration.

### Organizer and admin tests
- Organizer dashboard data is limited to assigned clubs/events.
- Revoking a club membership blocks that organizer from the club's resources and records an audit entry.
- Revoking the final active club membership revokes organizer role and clears trusted-publisher status.
- Participant lists and CSV exports are limited to authorized users.
- Export values are protected against CSV formula injection.
- Trust grants/revocations create audit records.

## 20. Implementation alignment and remaining decisions

This section records cross-document alignment rules and the few implementation choices that remain environment- or policy-dependent. The confirmed behavior below should be implemented consistently; remaining deployment choices should be finalized before production release.

| Gap / decision | Current API treatment | Required follow-up |
|---|---|---|
| Event eligibility and contact details | Added to the event schema as optional `eligibility_notes` and `contact_email` fields | Keep database, API, and frontend schemas aligned |
| Student cancellation cutoff | Confirmed: cancellation is allowed strictly before event start | Enforce with server time against `events.starts_at` |
| Email verification delivery provider and link/code format are undecided | API accepts a single-use token | Select provider and implementation format; do not expose raw tokens in logs |
| Verification resend | Added as `POST /auth/resend-verification` with a generic response and configurable rate limits | Keep token invalidation and rate limits covered by tests |

### 20.1 Database alignment

## 21. Implementation sequence

Recommended backend implementation order:

1. API foundation: FastAPI app, configuration, error envelope, OpenAPI metadata, CORS, health checks.
2. Database foundation: SQLAlchemy models, Alembic migrations, seed data, and test database.
3. Authentication: registration, verification, login, refresh rotation, logout, and password reset.
4. Current-user and authorization dependencies: user context, role checks, college scope, club membership checks.
5. Event discovery and categories: public listing, filters, detail response.
6. Organizer event workflow: draft creation, editing, submit for approval, trusted direct publishing, cancellation.

8. Event revision workflow: proposal submission, pending queue, approval/rejection, content-version concurrency.
9. Registrations: registration, capacity locking, cancellation, reactivation, participant lists, and exports.
10. Automated tests: especially college isolation, authorization, revision consistency, and concurrent capacity.

Build the API contract and tests before integrating the corresponding frontend screens. Keep FastAPI's generated OpenAPI output as the executable reference for the implemented request and response schemas.
